# ZotWatch 0.4.6（Codex 版）审查意见

对象：用户提供的安装包 `zotwatch-0.4.6.zip`（只有构建产物，没有源码）。对照的是仓库里的 0.4.1 源码（`zotero-plugin/src`、`addon`）和设计文档 `docs/design-0.5-topics.md`。审查分四个方向：外部接口、课题追踪、调研引擎回归、界面与打包。前三个方向的每条意见都由另一个审查者独立复核过；界面方向的复核没有完成，其中第 7 和第 8 条（标题双击打开两次、HTML `<select>`）已经手工核对属实，第 2.2、2.4、2.6 条以及第 2、3、4 节里只引自界面方向的意见都未经复核。行号指安装包里的文件（`content/zotwatch.js` 是打包后的引擎），标注 0.4.1 的指仓库源码。

## 先说结论

- **保留：**
  - 推荐卡片上的「相关文献」面板。按需加载，可取消，有缓存，加载、出错、空结果都有对应状态；
  - 课题的独立存储和写入队列；
  - 每次请求都计入预算；
  - 全程没有 `innerHTML`，也没有伪造请求头；
  - 调研引擎完整保留了 0.4.0 / 0.4.1 的所有修复。
- **发布前必须处理三件事：**
  - 构建方式：代码是直接改的打包产物，源码里没有；
  - Connected Papers 默认走网站的内部接口；
  - 多账号凭证池（含轮询）。
- **课题追踪：** 能用，但有几处会让它很快不好用：无 Key 时第二次检查起就卡死；一次检查能塞进几千篇「未查看」；每次点击都全量比对文库。设计里的自动检查、提醒和未读提示都还没做。

## 1. 发布前必须处理

### 1.1 改动没有进源码，无法重新构建（最重要）

- **现象：** `content/zotwatch.js` 里有 56 行未转义的中文，全部是新增的凭证池、Connected Papers、课题和相关文献代码（如第 370、426、4848、5233、5650–6684、7783–7906、8253、8571–9006、9546 行）。同一个函数里转义行和未转义行交替出现，例如 `resetData` 的第 9546 行和第 9547–9549 行。我们的构建脚本（`scripts/build.mjs`，esbuild `charset: "ascii"`）不可能产出这样的文件，说明这些代码是直接粘贴进打包产物的，没有经过 `npm run build` 和 `npm test`。
- **后果：** 下次从仓库 `npm run build`，这些功能会全部消失。反过来，如果保留 0.4.6 的窗口脚本、只重建引擎，`getApiPoolStatus`、`listTopics` 等调用会直接报错。新代码也没有任何测试。
- **版本冲突：** 安装包用的是我们的插件 ID 和 `update_url`，版本 0.4.6，但没有更新清单（`zotwatch-update.json`），帮助链接指向并不存在的 `zotero-plugin-v0.4.6` 标签。装了它的用户收不到 0.4.2–0.4.5，等 0.5.0 发布时又会被直接覆盖。
- **要求：**
  - 把改动写进 `src/` 和 `addon/`（例如 `src/survey/tracking.js`、`src/core/http.js`、`src/zotero/addon.js`），并按设计第 6 节补测试；
  - 用 `npm run build` 构建，构建后 `grep -P '[^\x00-\x7f]' build/addon/content/*.js` 应无输出；
  - 版本改为 0.5.0，CHANGELOG 加 `## 0.5.0`，同步更新 README 和 `CLAUDE.md`；
  - 0.4.6 这个包不要分发。

### 1.2 Connected Papers：默认走网站内部接口，并默认允许建图

- **现象：**
  - 默认是 `apis.connectedPapersMode = "public"`（`prefs.js:45`），调用的都是网站后端的未公开接口：`GET /id_translator/doi/…`（`connectedpapers.js:168`）、`POST /search/…/1`（:177）、`GET /graph_no_build/…`（:220），以及会让对方服务器开始建图的 `POST /graph/…`（:238）。返回的 `CPGR` 二进制帧是逆向解析的（:72–107）。
  - `apis.connectedPapersBuild` 默认为 true（`prefs.js:48`）。调研里勾选 Connected Papers 后会自动发建图请求（`zotwatch.js:6371`），收到 `OVERLOADED` 时也会发（`connectedpapers.js:235`），而推荐卡片上要手动点。
  - 设置页的说明直接写着沿用「Zotero Reference 的网站图谱流程」（`settings.js:2020`）。
- **为什么不行：** 设计文档第 0 节明确禁止调用 Connected Papers 的内部接口。这是在网站之外自动调用它不对外开放的接口，违反其使用条款。对方一改格式或封 IP，所有用户的这项功能都会失效。
- **另一个问题：** 「官方 API」模式的建图请求本身是对的：`GET /papers-api/graph/…` 加 `X-Api-Key`，状态值和官方 Python 客户端一致。但它解析种子 ID 时仍然调用上面两个内部接口（`resolveSeed`，`connectedpapers.js:158–193`）。
- **要求：**
  - 删除 public 模式：`decodePublicFrame`、`inflateConnectedPapers`、`graph_no_build` 和 `POST /graph` 都去掉。
  - 只保留官方 API，并满足：默认关闭；`connectedPapersBuild` 默认 false；收到 `OVERLOADED` 时不发建图请求；种子 ID 改用 Semantic Scholar 的公开 Graph API 解析（DOI → paperId，现有的 `s2SeedIds`、`s2ByTitle`），解析不了的跳过并提示。
  - 隐私说明（设置页和 README）写明：使用时会把种子或推荐文献的 DOI、标题发给 Connected Papers。
  - 设计里的「相似研究」用 OpenAlex 的文献耦合实现（设计 1.3 的 `rel:seed<n>`），不依赖 Connected Papers。

### 1.3 凭证池：一个服务多个 Key，含轮询

- **现象：** `api-pool.js` 给 OpenAlex 和 Crossref 各支持最多 11 个凭证，策略有「主备」和「轮询（round-robin）」（`api-pool.js:102、233–258`，设置页 `settings.js:105–117`）。
- **它做对的部分：** 收到 429、403 或额度用尽时整个服务一起暂停，不换 Key 继续请求（:316–338）。持久化的状态里只有指纹，没有 Key 本身。
- **为什么还是不行：**
  - 「轮询」会把一个人的请求平摊到多个账号的每日额度上，正是设计第 0 节禁止的用法。
  - 凭证池还带来了三个回归（见 2.1–2.3）。
- **建议：**
  - 去掉凭证池，恢复 0.4.1 的 `request()`（`src/core/http.js:211–236`），每个服务一个 Key，2.1–2.3 会一起消失。
  - Crossref Metadata Plus 是付费订阅，可以作为单个 Token 字段保留。

## 2. 功能缺陷与回归

### 2.1 回归：OpenAlex / Crossref 的 429 不再等待重试，直接失败

- **现象：** 收到不带 `Retry-After` 的 429 时，凭证池凭空设置 60 秒的整站冷却（`api-pool.js:326、337`）。之后的重试和其他排队请求都会立刻抛出 `API_POOL_COOLDOWN`，而 `request()` 直接把它抛出去，不重试（`zotwatch.js:413`）。这两个服务也不再走限速器的 `pause`（:431–434）。0.4.1 的做法是按 2 秒、4 秒退避重试，并让同一服务的队列一起等待。
- **后果：**
  - 每日推荐：Crossref 两个抓取任务并行，一个 429 就让当天没有期刊候选。
  - 调研：OpenAlex 连续三个任务瞬间失败，触发「连续失败 3 次，跳过其余请求」，剩下的检索和扩展全部丢掉。
- **修复：** 去掉凭证池即可。如果保留，只在额度真正用尽时（剩余为 0、每日额度提示、或 `Retry-After` 超过上限）才设冷却；短暂限流恢复 0.4.1 的路径：暂停限速器、等待后重试。

### 2.2 回归：网络错误变成英文的 "API service request failed."

- **现象：** 凭证池吞掉了原始错误（`api-pool.js:290–296`）。0.4.1 会显示「网络连接失败：主机（0x…）」，现在看不出是哪台服务器、什么原因。
- **修复：** 重新抛出原来的错误（它本身已经隐去了 Key）。

### 2.3 冷却期间填了新 Key 也不生效，连测试都做不了

- **现象：** 整站冷却保存在偏好设置里，重启后还在（`api-pool.js:133–140`）。更换凭证时不会清除冷却（`configure()`，:101–121），「测试接口」也先被冷却挡住（:268）。
- **后果：** 不填 Key 的新用户用完免费额度，按提示填上 Key 后，最长约 24 小时内 OpenAlex 仍然完全不可用。0.4.1 填上新 Key 立刻生效。
- **修复：** 去掉凭证池；或者在凭证变化时清除冷却，测试请求不受冷却限制。

### 2.4 「相关文献」标题点一次打开两个标签页

- **现象：** `inbox.js:384` 的链接自己处理了点击，调用了 `preventDefault()` 和 `openUrl`，但没有调用 `stopPropagation()`。`main.js:607–613` 的全局点击处理又打开了一次。0.4.1 的推荐卡片标题有 `stopPropagation()`，正是为了避免这个问题。
- **修复：** 加 `event.stopPropagation()`，或者去掉这里的 onclick，交给全局处理。

### 2.5 方向选择用了 HTML `<select>`

- **现象：** `topics-ui.js:233–235` 用了 `<select>`。这个项目的运行约束禁止 HTML `<select>`：在 Zotero 的 XUL 窗口里下拉弹层显示不正常。
- **修复：** 改用现有的分段按钮、单选列表，或者搜索框组件（`search.js`）。

### 2.6 正在进行的课题检查，关窗再开后看不到也停不了

- **现象：** 界面只按窗口自己的 `state.busy` 判断检查是否在进行，忽略了 `listTopics` 和 `getTopic` 返回的 `running`、`progress`（`topics-ui.js:78–83、165–171`）。检查在关窗后会继续，新窗口却显示「检查新增」。点「删除课题」会提示「请先取消课题检查」，可界面上没有停止按钮。
- **修复：** 把 `topic.running` 当作进行中，显示进度和「停止检查」；检查结束时刷新列表；事件触发的重新加载要做防抖。

## 3. 课题追踪

### 3.1 不填 OpenAlex Key 时，第二次检查起整个课题卡死（高）

- **现象：** 不填 Key 时，翻到第 2 页就抛 `TOPIC_KEY_REQUIRED`（`zotwatch.js:7896–7901`），这个分支一直处于「待续」（`topics.js:481–503`）。之后每次检查，只要有分支待续，其他所有分支和未解析的种子都会被跳过（:394、401–404、438）。
- **后果：** 结果是 0 请求、0 新增，永远如此，只有改配置才能解开，而改完下次又会卡住。另外，不填 Key 时第一页也带了 `cursor=*`，0.4.1 正是因为「无 Key 不能用 cursor 翻页」才刻意不带 cursor。
- **修复：**
  - 不填 Key 时只读一页、不带 cursor，在界面上注明「未配置 Key：只取前 100 条」；
  - 每个分支独立判断要不要续读，去掉全局的 `pendingAtStart` 过滤和种子延后；
  - 同一分支连续失败约 3 次，或遇到 `TOPIC_KEY_REQUIRED` 等 4xx 错误时，关闭这个时间窗并记录错误，下次重新开始。

### 3.2 没有相关度过滤和 30 篇上限，「未查看」会塞进几千篇（高）

- **现象：**
  - 每个分支把整个时间窗翻到底：每页 100 条，最多 200 页，首次窗口 90 天，最长可设 3650 天。
  - 结果全部按「新」保存，上限 5000 篇（`topics.js:6、455–505`）。
  - 排序只看标题和摘要的词重合（`rankPapers`），不做任何过滤。
  - 每次检查的预算默认 50，最高 200。
- **后果：** 一个由 5 个标签关键词建成的课题，一次检查就能加进几千篇关系松散的论文。
- **修复：** 按设计 1.3 来：
  - 每个分支每次只读一页：引用种子的每页 100 条，检索每页 25 条；
  - 预算默认和上限都设为 30；
  - 时间窗为上次检查减 14 天；首次检查用调研完成时间减 30 天，由研究方向建的课题用当前时间减 30 天；
  - 合并后最多向量化 300 篇，用「主题文字 + 种子向量」的中心打分（同 `stage_rank`）；
  - 相似度低于原候选池中位数的丢弃，只保留前 30 篇作为新增；
  - 删除超量数据时，不删用户标记过「稍后阅读」或「不相关」的论文。

### 3.3 「创建追踪课题」把整个候选池当成未查看，重复点击还会重复创建（中）

- **现象：** `createTopicFromSurvey` 把 `survey.pool` 作为基线、状态为「新」写入（`zotwatch.js:8690`，`topics.js:288–291、566–567`）。一项标准调研，课题一建好就显示「400 篇未查看」，而且全是用户刚在调研里看过的。
- **修复：**
  - 候选池只用于去重，状态设为已查看，不计入新增；
  - 如果已有 `originSurveyId` 相同的课题，直接打开它，按钮改为「打开追踪课题」。

### 3.4 每次点击都把课题里的每篇论文和整个文库逐条比对（高，性能）

- **现象：** `decorateTopic` 每次都重新读取整个文库（`zotwatch.js:8569–8577`），再对课题里的每篇论文线性扫描两遍文库，对每个条目做 DOI 和标题规范化（:7851–7855）。获取课题、标记已查看、稍后阅读、保存课题、检查结束，都会调用它，一次操作往往调用两次。
- **后果：** 3000 篇的课题加 8000 条的文库，每点一次「已查看」就要在主线程做约 4800 万次规范化，Zotero 会卡住好几秒。
- **修复：** 每次比对时先建好「DOI → 条目」和「标题 → 条目」两张映射表，按文库缓存，用 Zotero Notifier 监听条目变化来失效。界面直接用 API 返回的结果，不再调用 `getTopic` 重新拉取。

### 3.5 其他（低）

- **研究方向关键词混入输出标签：** 方向关键词会混入 ZotWatch 输出标签和只有符号的标签，它们又被当成检索词（`topic-profile.js:33–41`）。改用 0.4.1 的 `isKeywordTag`（`src/core/topics.js:19–24`）过滤。
- **找不到的种子反复解析：** OpenAlex 中找不到的种子，每次检查都重新解析，可能耗光预算（`topics.js:395–424`）。应记下「未找到」，过一段时间再试。
- **课题检查和其他任务并行：** 课题检查会和每日推荐、调研同时跑，也不会被它们取消（`zotwatch.js:8692–8708`）。按设计 1.4：推荐运行或调研开始时取消检查，进行中不启动检查。
- **文库不可用的课题打不开也删不掉：** 课题所在文库不可用时，打开和删除都会失败（`zotwatch.js:8569–8571、8648–8660`）。删除不应依赖文库。
- **种子选择没用向量：** 由研究方向挑种子用的是关键词重合，可文库条目的画像向量已经有了（`zotwatch.js:3921、4051`）。按设计用「最接近方向中心的条目」。

## 4. 设计里还没做的部分

逐项实现，或者在设计文档里明确改为下一版：

| 设计条目 | 现状 |
|---|---|
| 1.4 自动定期检查（每轮最多 3 个课题） | 没有，只能手动检查（manifest 写的是「手动追踪」） |
| 1.4 有新增时通知；左侧栏「调研」徽标 | 没有 |
| 1.5 概览页「课题追踪」卡片；「研究方向」卡片的「建为课题」 | 没有，从研究方向建课题的入口在调研页 |
| 1.3 相关论文分支（文献耦合 `rel:seed<n>`） | 没有，相关文献只能走 Connected Papers |
| 2 「已收藏·未读」提示，以及 `library.readTag` / `unreadTag` / `unreadHints` | 没有，界面写的是「阅读状态未知」 |
| 3 覆盖统计；4 每次检查各步数量和采纳统计 | 没有 |

另外，课题被做成了独立于调研的一套模型。这本身可以接受，好处是不受「调研记录最多 30 条」的限制，写入也不会和调研冲突。但设计里「从调研开启追踪」的体验要靠 3.3 的修复补上。

## 5. 体验细节（低）

- **课题面板整块重建：** 每次刷新都重建整个面板，焦点、正在输入的内容、展开状态和滚动位置都会丢失（`topics-ui.js:93–107、198–206`）。应只更新变化的部分，或刷新前后保存并恢复这些状态。
- **「立即检查」没有反应：** 研究画像在更新时点「立即检查」，界面没有任何反馈（`zotwatch.js:8085–8088、8605–8628`）。应提示原因。
- **「相关文献」面板：** 切换页面会取消加载，焦点也会丢失（`inbox.js:270–319`）。
- **「学术数据接口」设置太复杂：** 去掉凭证池和 Connected Papers 的公开模式后，这一页会简单很多。
- **Crossref 邮箱前后不一致：** 凭证池会去掉格式校验不通过的 Crossref 邮箱，而限速器仍把它当作礼貌池（`api-pool.js:103–104、191–198`）。去掉凭证池后这个问题随之消失。
- **Connected Papers 的出错提示：** 「稍后重试」类错误不能重试，原始 HTTP 错误还会写进保存的笔记（`connectedpapers.js:234、252`；`zotwatch.js:6718–6745`）。
- **排序权重：** Connected Papers 图谱里的论文和直接引用拿同样的「与种子关联」分（`zotwatch.js:5034–5040`）。改成和 Semantic Scholar 推荐一样的封顶加分（合计 +1），「先前工作」不加分。

## 6. 建议的处理顺序

1. 让 Codex 交出源码改动，在 `src/` 里实现，过 `npm test` 和 `npm run build`，版本改为 0.5.0（1.1）。
2. 删除 Connected Papers 的公开模式和凭证池（1.2、1.3）。这样 2.1–2.3 和第 5 节里凭证池相关的两条也一起解决。
3. 修复课题追踪的 3.1–3.4 和界面的 2.4–2.6。
4. 按第 4 节补齐自动检查、通知、徽标、概览卡片，以及「已收藏·未读」。
